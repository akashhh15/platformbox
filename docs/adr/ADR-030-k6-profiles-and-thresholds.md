# ADR-030: k6 profiles and provisional thresholds

- **Status:** Accepted
- **Date:** 2026-11-25
- **Deciders:** platform maintainers

## Context

Phase 9 needs repeatable load profiles that can prove HPA scaling on `kind` and
Karpenter scale-out on the optional EKS path. ADR-024 defines the API SLOs
(99.5% availability and p95 below 500 ms), but no real baseline has been
measured in this environment: the Docker daemon was unavailable for live runs,
and `AGENTS.md` forbids invented reliability figures. A spike profile also
needs guardrails that are deliberately looser than the SLO.

## Decision

Commit three k6 2.4.0 profiles under `loadtest/`:

- `smoke.js`: 1 VU for 30s, zero failed requests and all checks passing.
- `load.js`: ramp to 10 VUs, hold 50 VUs for five minutes, ramp down; error
  rate below 0.5%, checks above 99%, p95 below 500 ms. The long plateau allows
  several HPA sync periods and observation of scale-down stabilisation.
- `spike.js`: ramp from 5 to 100 VUs in 10s, hold 30s, ramp down; error rate
  below 5%, checks above 95%, p95 below 2 s. These are stress guardrails, not
  SLOs.

All three call `GET /items`, accept `BASE_URL` as an environment override and
use k6 thresholds that exit non-zero on breach. `abortOnFail` is not set: the
sustained profile must finish so recovery can be observed. The thresholds are
marked as provisional in the scripts and docs, and every result field in the
game-day template stays `TODO(measure)` until a human runs the profile.

## Alternatives considered

| Alternative | Why it was not chosen |
|---|---|
| Prometheus-based validation during the run | Adds a dependency on a live cluster and dashboard; k6 thresholds give a deterministic exit code offline and in CI. |
| One fixed-VU profile | A step load cannot show HPA scale-up timing or recovery after a spike, which are the behaviours under test. |
| Measured thresholds now | No live run has happened; writing observed-looking numbers would violate `AGENTS.md`. |
| `abortOnFail: true` | Would end the load profile at the first breach and hide recovery behaviour. |

## Consequences

- Profiles are syntax-checked by `scripts/resilience-validate.sh` with pinned
  k6 2.4.0; no load is generated by the agent or CI.
- A human must run the profiles, replace the provisional values with measured
  baselines and update ADR-024 if the SLO thresholds need to change.
- HPA proof needs `metrics.k8s.io`; Karpenter proof needs an explicitly approved
  paid EKS cluster. Both prerequisites are documented in `docs/resilience.md`.
